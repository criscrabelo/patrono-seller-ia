03/10/2026. Base: P2.11, seção 5 (limite do bucket e objetos órfãos).
Implementado e validado só contra o ambiente de **teste** (projeto Supabase
de teste, sa-east-1). Sem deploy, sem migration. Netlify, Vercel, DNS, OAuth
e Supabase de produção não foram alterados.

## Decisões aprovadas (revisão da P2.12)
- `UPLOADS_ORFAOS_PRAZO_HORAS` = **24** (é também o padrão do código).
- `digital-twin-private` com limite de **50 MB** no go-live, aplicado pelo
  script com ensaio e `--confirmo-producao`. **Nada de SQL manual em produção.**
- `previews/` continua **fora** desta limpeza.
- A rotina entra em produção **só em ensaio**: `LIMPEZA_UPLOADS_ORFAOS_ATIVA`
  fica ausente. Ligar a exclusão, depois de alguns dias de relatórios, é
  decisão separada.
- Horário **04:30 UTC** na Netlify e no GitHub; só o agendador declarado em
  `AGENDADOR_DOS_CRONS` dispara.

## 1. Auditoria (ambiente de teste, somente leitura)

| Pergunta | Resposta |
|---|---|
| Configuração do bucket hoje | `digital-twin-private`: `public: false`, `file_size_limit: null` (valia só o limite global do projeto), `allowed_mime_types: null` |
| Conteúdo | 13 objetos: 6 sob `<workspace>/<perfil>/` (referências) e 7 sob `previews/<perfil>/` (prévias do worker). Os 13 têm `DigitalTwinAsset`: **nenhum órfão hoje** |
| O que distingue confirmado de órfão | **Confirmado** = existe `DigitalTwinAsset.storagePath` igual ao caminho. A confirmação (passo ③) é o único ponto que cria o registro do upload direto. **Órfão** = objeto no padrão do upload direto sem esse registro |
| Idade do objeto | Duas fontes, as duas do servidor: o carimbo no caminho (`<tipo>-<epoch ms>-<12 hex>`, gerado no passo ①) e `created_at`/`updated_at` do storage |
| Dá sem migration? | **Sim.** Listagem pela API do Storage (só o prefixo `<workspace>/<perfil>/`), consulta a `DigitalTwinAsset` por `storagePath` e exclusão pela API do Storage. Nenhuma tabela ou coluna nova. Não se apaga linha de `storage.objects` por SQL (deixaria o arquivo físico) |

### Prazo seguro
- Intenção de confirmação: 10 min (`VALIDADE_DA_INTENCAO_MS`).
- Token de envio do Supabase: 2 h (fixo no Supabase) — o PUT pode chegar até 2 h depois do passo ①.
- **Prazo adotado: 24 h** contadas do **mais novo** entre carimbo do caminho, `created_at` e `updated_at`. Ajustável por `UPLOADS_ORFAOS_PRAZO_HORAS` entre **3 h e 720 h**; valor inválido ou fora disso volta a 24 h.
- Além disso, um objeto com carimbo dentro de 10 min + 2 h nunca é elegível, qualquer que seja o prazo informado.

### O que nunca pode ser apagado
1. Objeto com `DigitalTwinAsset` em **qualquer** workspace (confirmado, ativo ou não).
2. Objeto fora do padrão exato do upload direto — inclusive `previews/...` (prévias, já tratadas pela retenção da Rodada 8), evidência de consentimento, `consent_evidence`/`generated_preview` no nome, subpastas e extensões.
3. Objeto de outro workspace ou de outro perfil: só se lista `<workspace>/<perfil>/` de perfis existentes no banco; o caminho precisa bater com os dois.
4. Objeto recente, sem data no storage ou com carimbo no futuro.

## 2. Limite de 50 MB no bucket

`LIMITE_DO_BUCKET_BYTES` (`lib/digital-twin-upload-direto.ts`) = maior limite
por tipo = **52428800 bytes (50 MB, vídeo)**. É a segunda barreira: o storage
recusa o PUT acima disso mesmo que alguém pule a validação do passo ①.

### Teste — aplicado
```
node --env-file=.env.digital-twin-test scripts/limite-bucket-digital-twin.mjs            # ensaio
PATRONO_REF_DO_BANCO_DE_PRODUCAO=<ref-prod> node --env-file=.env.digital-twin-test \
  scripts/limite-bucket-digital-twin.mjs --aplicar
```
Resultado: `file_size_limit: null → 52428800`, `public: false` mantido,
`allowed_mime_types` inalterado. Segunda aplicação: "Já aplicado". Sem a
referência de produção, o script recusa aplicar.

Validação real: PUT de **50 MB + 1 byte** pela URL assinada → recusado pelo
storage (objeto não existe); PUT de **exatamente 50 MB** → aceito (e apagado
em seguida). Isso também prova que o limite global do projeto de teste é ≥ 50 MB.

### Produção — NÃO aplicado. Passo do go-live

**Script (forma aprovada — confere antes e depois, mantém privado):**
```
PATRONO_REF_DO_BANCO_DE_PRODUCAO=<ref-prod> \
NEXT_PUBLIC_SUPABASE_URL=https://<ref-prod>.supabase.co \
SUPABASE_SERVICE_ROLE_KEY=<service role de produção> \
node scripts/limite-bucket-digital-twin.mjs                                  # 1º: ensaio, ler a saída
… mesmo comando … --aplicar --confirmo-producao                              # 2º: aplica
```
Sem `--confirmo-producao` o script recusa a produção.

**Só como referência, NÃO usar nesta fase** (aprovado: script, não SQL manual).
O que o script faz equivale a:
```sql
-- conferir antes
select id, public, file_size_limit, allowed_mime_types from storage.buckets where id = 'digital-twin-private';
-- aplicar (só se public = false)
update storage.buckets set file_size_limit = 52428800 where id = 'digital-twin-private' and public = false;
-- conferir depois: public = false, file_size_limit = 52428800
select id, public, file_size_limit, allowed_mime_types from storage.buckets where id = 'digital-twin-private';
```

**Antes de aplicar:** em Storage → Settings, o limite global de upload
do projeto de produção precisa ser **≥ 50 MB** (o do bucket não passa do
global). Não foi verificado na produção nesta rodada.

**Atenção:** as prévias do worker (`previews/...`) vão para o mesmo bucket.
Uma prévia acima de 50 MB passaria a ser recusada. As 7 prévias de teste
somam 4,6 MB (todas bem abaixo).

## 3. Limpeza dos uploads órfãos

```
Scheduled Function  netlify/functions/rotina-limpar-uploads-orfaos.ts  (04:30 UTC)
GitHub Actions      .github/workflows/patrono-crons.yml, agenda própria '30 4 * * *'
  └─ dispararRotina('limpar-uploads-orfaos', …, '?modo=execucao')        (netlify/rotina-interna.ts)
       └─ GET /api/cron/limpar-uploads-orfaos                            (app/api/cron/…/route.ts)
            └─ executarLimpeza(porta real)                               (lib/limpeza-uploads-orfaos.ts)
                 └─ Prisma (perfis, assets) + Storage API (listar, apagar)  (lib/limpeza-uploads-orfaos-porta.ts)
```
O arquivo nunca é lido, baixado nem transferido: só nome, datas e tamanho
vindos da listagem.

### Um agendador por vez — regra ESTRITA nesta rota
`chamadaDoAgendadorDeclarado` (`lib/agendador.ts`): a rota só aceita a
chamada se `AGENDADOR_DOS_CRONS` estiver declarado **explicitamente**
(`github` ou `netlify`) **e** a chamada trouxer `x-patrono-agendador` igual
a ele. Caso contrário, **409** antes de tocar em banco ou storage.

| `AGENDADOR_DOS_CRONS` | GitHub (`x-patrono-agendador: github`) | Netlify (`netlify`) |
|---|---|---|
| `netlify` | **409** | executa |
| `github` | executa | **409** (e a Scheduled Function nem chama a rota) |
| ausente / vazio / outro valor | **409** | **409** (e a Scheduled Function nem chama a rota) |

As outras rotas de cron **não mudaram** (nelas, ausente continua = GitHub
aceito). O workflow passou a mandar `x-patrono-agendador: github` em todas
as chamadas (as outras rotas ignoram) e trata o 409 **desta** rota como
"recusa esperada", sem marcar falha; qualquer outro erro continua falhando.

### Horário
04:30 UTC nos dois. Na Netlify, `schedule: '30 4 * * *'`. No GitHub, o
despachante de hora em hora (minuto 0) não chama mais a limpeza; ela tem
agenda própria `'30 4 * * *'`, que roda **só** a limpeza (um job a mais por
dia, ~30 min/mês da cota). Disparo manual continua com `ensaio` como padrão.

### Disparo repetido ou simultâneo
- **Execução real exclusiva**: `pg_try_advisory_xact_lock` dentro de uma
  transação (funciona no pooler em modo transação, `pgbouncer=true`, e se
  solta sozinha no fim ou em queda). Uma segunda execução real simultânea
  não lista, não apaga e não audita; o relatório traz
  `outraExecucaoEmAndamento: true`. Ensaio não usa a trava.
- Achado durante os testes: sem essa trava, duas execuções simultâneas
  apagavam cada arquivo uma vez só, mas **as duas contavam** a exclusão
  (relatório e auditoria em dobro). Corrigido pela trava.
- Repetição sequencial: a segunda não encontra mais nada (idempotente).

### Desligada por padrão — cinco travas, todas precisam estar abertas
1. `AGENDADOR_DOS_CRONS` declarado, e a chamada vir dele;
2. na Netlify, `ROTINAS_NETLIFY_LIGADAS`, se definida, precisa incluir `limpar-uploads-orfaos`;
3. a chamada pede `?modo=execucao`;
4. `LIMPEZA_UPLOADS_ORFAOS_ATIVA=true` no app — **fica ausente no go-live**;
5. nenhuma outra execução real em andamento.

Faltando a 3 ou a 4, a rota roda em **ENSAIO**: relatório, nada apagado.

### Fail-closed
- Sem `CRON_SECRET` ou com segredo errado: 401. Agendador não declarado ou outro agendador: 409.
- Sem storage configurado (`uploadDiretoConfigurado`): **503, nada feito**.
- Falha ao listar um workspace: nada dele é apagado; os demais seguem (`falha: 'listagem'`).
- Falha ao consultar registros: nada é apagado naquele workspace (`falha: 'registro'`).
- Erro inesperado: 500 sem detalhe.

### Concorrência / confirmação em andamento
- Elegível só depois de 24 h (mín. 3 h); a confirmação só é aceita até 10 min após o passo ① → objeto elegível já não pode ser confirmado.
- Mesmo assim, os registros são **consultados de novo imediatamente antes de apagar**; o que tiver ganho asset nesse intervalo fica.
- Upload sem `upsert`: um objeto existente não é sobrescrito por outro envio.

### Proteção por workspace e relatório
- Lista apenas `<workspace>/<perfil>/` de perfis existentes; `?workspace=<id>` restringe a um só.
- Registro em qualquer workspace preserva o objeto.
- Relatório por workspace, só contagens: `objetosVistos, confirmados, foraDoPadrao, recentes, elegiveis, bytesElegiveis, apagados, falha?`. Nunca caminho, nome de arquivo ou id de perfil.
- Auditoria por workspace quando apaga: `digital_twin.uploads_orfaos_removidos` com `{ quantidade }`.
- Teto de 500 exclusões por execução; o restante fica para a próxima (idempotente).

### Variáveis (nenhuma definida; nada a mudar no painel agora)
| Variável | Padrão | Efeito |
|---|---|---|
| `LIMPEZA_UPLOADS_ORFAOS_ATIVA` | ausente | `true` libera a execução real |
| `UPLOADS_ORFAOS_PRAZO_HORAS` | 24 | 3–720; inválido = 24. Aprovado: 24 |
| `AGENDADOR_DOS_CRONS` | (existente, P2.2) | precisa estar declarado (`github` ou `netlify`) para esta rotina rodar |
| `ROTINAS_NETLIFY_LIGADAS` | (existente, P2.9) | incluir `limpar-uploads-orfaos` para a Scheduled Function chamar |

Go-live (aprovado): a rotina entra **só em ensaio** — Scheduled Function
ligada, `LIMPEZA_UPLOADS_ORFAOS_ATIVA` ausente. Depois de alguns dias de
relatórios nos logs, ligar a exclusão é decisão separada.
